# ARMory MCP для Codex и других клиентов

ARMory предоставляет Kanban-инструменты по протоколу MCP. В репозитории ARMory Codex запускает локальный stdio-сервер из проектной конфигурации. HTTP endpoint остаётся доступен другим MCP-клиентам.

Общие инструкции и схемы инструментов MCP задаются сервером ARMory и применяются ко всем проектам и подключённым агентам независимо от открытого репозитория.

Команда `/task` включает работу через Kanban, где бы она ни находилась в сообщении пользователя. Без неё новые обычные поручения не превращаются в карточки автоматически. Для уже существующей задачи пользователь может указать её номер.

## Возможности

- `list_projects` — найти проекты ARMory по названию.
- `list_task_statuses` — получить колонки проекта.
- `list_tasks` — получить список задач проекта.
- `create_task` — создать задачу с обязательной оценкой в минутах, выбрав проект по имени или ID; по умолчанию используется первая колонка проекта.
- `get_task` — получить задачу по глобальному номеру, без ID проекта.
- `take_task_into_work` — перевести задачу в распознанную колонку «В работе», назначить AI-исполнителя и запустить учёт времени.
- `start_task_time` и `pause_task_time` — возобновить или приостановить активную сессию агента по задаче.
- `update_task_time` — вручную задать план, время работы, тестирования и факт в минутах; меняются только переданные поля, сессия агента не запускается. Если передать работу или тестирование без факта, факт пересчитывается по этапам.
- `update_task` — изменить выбранные поля задачи.
- `complete_task` — переместить задачу в финальную колонку и записать результат. Инструмент не архивирует задачу и не меняет `is_closed`.
- Исполнителей MCP принимает в `assignee_names` как отображаемые имена. Email нужен API как внутренний идентификатор, агенту не нужно запрашивать его у пользователя.
- `get_task` и `list_tasks` возвращают исполнителей по именам. Передавайте в `update_task.assignee_names` весь желаемый список: он заменяет текущих исполнителей.
- `take_task_into_work` добавляет AI Assistant к текущему списку исполнителей, не удаляя уже назначенных людей.
- При создании задачи HTTP-клиентом MCP назначает вошедшего OAuth-пользователя и AI Assistant, если пользователь найден в справочнике исполнителей. Если сопоставление не удалось, задача создаётся с AI Assistant и результат содержит `assignee_prompt_required: true`: сообщите об этом и предложите пользователю указать исполнителя. После ответа получите текущих исполнителей через `get_task` и передайте полный список через `update_task.assignee_names`, сохранив AI Assistant. В публичном режиме клиент только с API-ключом назначает AI Assistant. Локальный HTTP-сервер (`AUTH_REQUIRED=false`) без подтверждённого пользователя и stdio-сервер используют `MCP_LOCAL_ASSIGNEE_NAME` из `.env`.
- При создании каждой задачи через MCP обязательно передавайте плановую оценку `estimated_minutes` в целых минутах.
- После реализации переведите задачу в «Тестирование» и проведите собственные проверки. После проверок остановите таймер, оставив карточку в «Тестировании». Перевод в «Деплой» выполняйте только по прямой просьбе пользователя.
- Для записи времени уже выполненной задачи используйте `update_task_time`, а не описание или результат задачи. Значения плана, работы, тестирования и факта передаются в минутах.
- `take_task_into_work` переводит карточку в «В работе» и запускает таймер `work`. После реализации агент переводит карточку в «Тестирование» через `update_task`: смена стадии закрывает рабочий интервал и запускает таймер `testing`. Затем агент сам проверяет результат. Если нужны исправления, вызовите `take_task_into_work`, а перед повторными проверками снова переведите карточку в «Тестирование».
- При любой остановке работы или тестирования, ожидании ответа пользователя и перед финальным ответом вызывайте `pause_task_time`, независимо от статуса карточки. При продолжении того же этапа вызовите `start_task_time` с соответствующей фазой. Паузы между интервалами не входят в фактическое время.
- После завершения собственных проверок вызовите `pause_task_time` с `completed=true`, затем `update_task` для записи результата, оставив карточку в «Тестировании». Обновление описания, результата, исполнителей или повторная передача текущего статуса не запускает и не возобновляет таймер. При новой просьбе пользователя доработать эту задачу снова вызовите `take_task_into_work`: карточка возвращается в «В работе», начинается новый рабочий интервал, накопленное время сохраняется.
- Одновременно для одной MCP-сессии учитывается не более одной активной задачи: запуск времени на другой задаче закрывает предыдущую сессию агента. Изменение статуса закрывает активные интервалы по задаче.
- MCP Streamable HTTP использует состояние сессии, чтобы различать параллельных агентов. После изменения MCP-инструментов переподключите клиент для загрузки новой схемы.

Если название проекта неоднозначно, MCP вернёт подходящие проекты, чтобы Codex уточнил выбор. Если в проекте не удаётся определить колонку «В работе», MCP вернёт доступные колонки, а не выберет статус наугад.

## Настройка ARMory

1. Задай `MCP_API_KEY` в окружении сервера ARMory. Сгенерируй отдельный случайный ключ и передавай его клиентам безопасным способом.
2. Для публичного режима настрой auth gateway так, чтобы браузерный OAuth-вход для `/mcp/authorize` и `/mcp/oauth/complete` проходил через него. Gateway должен пропускать MCP endpoint, OAuth metadata, а также `/mcp/register` и `/mcp/token`. Остальные HTTP-вызовы защищаются OAuth-токеном или API-ключом в ARMory:

```yaml
- OAUTH2_PROXY_SKIP_AUTH_ROUTES=^/wopi/.*$,^/mcp$,^/mcp/$,^/mcp/(token|register|revoke)$,^/mcp/\.well-known/(oauth-authorization-server|oauth-protected-resource)$,^/\.well-known/oauth-protected-resource$,^/\.well-known/oauth-protected-resource/mcp$,^/\.well-known/oauth-authorization-server/mcp$
```

3. Перезапусти ARMory. Streamable HTTP endpoint доступен по адресу `https://<your-domain>/mcp/`. Завершающий слэш обязателен: адрес `/mcp` перенаправляется на `/mcp/`, а MCP-клиент может не поддержать такой редирект.

После изменения состава инструментов или их аргументов переподключи MCP-клиента, чтобы он загрузил новую схему и общие инструкции сервера.

При запуске ARMory обновляет старое SQLite-хранилище OAuth: переименовывает `mcp_oauth_clients.client_data` в `client_info` и преобразует числовые даты истечения и отзыва токенов в формат текущих моделей. Перед изменениями создаётся резервная копия в `data/backups/`. Клиенты, токены и задачи не удаляются. На уже обновлённой базе повторное преобразование не выполняется.

Для запросов с OAuth пользовательская личность берётся из выданного MCP OAuth-токена. Старые клиенты с `Authorization: Bearer <mcp-api-key>` продолжают работать без идентификации человека.

## Подключение Codex в папке ARMory

В репозитории уже есть `.codex/config.toml`: он запускает `scripts/armory-mcp.sh` только для проекта ARMory. Скрипт читает `MCP_API_KEY` и `ARMORY_BASE_URL` из локального `.env` приложения. Ключ не нужно копировать в конфигурацию Codex.

```toml
[mcp_servers.armory]
command = "scripts/armory-mcp.sh"
default_tools_approval_mode = "writes"
```

Открой папку репозитория ARMory в Codex и перезапусти сессию после изменения конфигурации. Проектную `.codex/config.toml` Codex загружает только для доверенных проектов. Проверь подключение:

```bash
codex mcp list
```

В открытой сессии команда `/mcp` должна показать сервер `armory` и его инструменты.

Для работы с ARMory из другого репозитория MCP-сервер подключается в `.codex/config.toml` того проекта отдельно. HTTP-конфигурация выглядит так:

```toml
[mcp_servers.armory]
url = "https://<your-domain>/mcp/"
http_headers = { "X-MCP-API-Key" = "<mcp-api-key>" }
default_tools_approval_mode = "writes"
```

Перенеси текущее значение ключа из `Authorization` в `X-MCP-API-Key`, не меняя сам ключ: Codex использует `Authorization` для OAuth. Один раз запусти `codex mcp login armory` и заверши вход в ARMory в браузере. Codex будет обновлять OAuth-токен автоматически. Сохрани завершающий слэш в URL.

## Работа с задачами

`pause_task_time` принимает `completed`: при ожидании ответа или временной паузе передавайте `false`, после завершения порученной работы и проверок — `true`. Это меняет «Статус времени», не перемещая карточку в финальную колонку. Возобновление через `start_task_time` или `take_task_into_work` снова показывает «В работе» и сохраняет накопленное время.

Пути к проектам и файлам, явно указанные в промпте, передавайте списком `input_paths` в `create_task` или `update_task`. Каждый путь сохраняется без изменений как вложение типа `link` с названием и адресом, равными исходному пути. Сервер не читает и не загружает файлы; локальный путь остаётся вводной для агента и не становится файлом для скачивания. Повторные пути не добавляются, существующие вложения сохраняются. `input_paths_errors` перечисляет пути, которые не удалось сохранить: карточка и успешные вложения остаются, повторите `update_task` с этими путями после устранения ошибки.

Если автоматическое назначение пользователя не сработало, `create_task` возвращает `assignee_resolution_error` с конкретной причиной:

- `authenticated_user_missing` — в HTTP-запросе к серверу с `AUTH_REQUIRED=true` нет личности пользователя; один API-ключ её не содержит.
- `assignee_directory_unavailable` — сервер не смог прочитать справочник исполнителей.
- `authenticated_user_not_in_assignee_directory` — пользователь определён, но его email отсутствует в справочнике исполнителей.
- `authenticated_user_display_name_missing` — пользователь найден, но у него не заполнено отображаемое имя.
- `local_assignee_not_configured` — для stdio-подключения или локального HTTP-сервера (`AUTH_REQUIRED=false`) без подтверждённого пользователя не задан `MCP_LOCAL_ASSIGNEE_NAME`.

Создание карточки с AI Assistant сохраняется. Если других исполнителей нет, `assignee_prompt_required: true` означает, что агент должен предложить пользователю указать исполнителя. Этот признак сам по себе не означает ошибку OAuth.

Команду `/task` распознавайте в любом месте сообщения. Если сразу после неё указан номер задачи, загрузите эту задачу через `get_task`; новую карточку вместо неё не создавайте. Если после `/task` номера нет, создайте новую задачу через `list_projects` и `create_task`, укажите плановую оценку в минутах. HTTP-клиент после OAuth-входа назначает вошедшего пользователя, если тот найден в справочнике, и AI Assistant. Если сопоставление не сработало, задача всё равно создаётся с AI Assistant; при `assignee_prompt_required: true` сообщите об этом и предложите пользователю указать исполнителя. Для выполнения задачи вызовите `take_task_into_work` и начинайте изменения после успешного ответа: инструмент переводит задачу в «В работе» и запускает рабочий таймер. Если пользователь просит только зарегистрировать задачу, оставьте её в первой колонке без запуска таймера. При ошибке сообщите точную ошибку и не начинайте изменения. Без `/task` новую Kanban-карточку автоматически не создавайте.

`/task <описание>` означает создать новую задачу с оценкой. При HTTP OAuth-входе MCP назначает вошедшего пользователя, если он найден в справочнике, и AI Assistant. Если пользователь не найден, задача создаётся с AI Assistant, а агент сообщает об этом и предлагает указать исполнителя через `update_task.assignee_names`. `/task <номер>` означает загрузить существующую задачу с таким номером и, если поручено выполнение, взять её в работу. Номер может быть записан с `#`. Если пользователь просит только зарегистрировать задачу без выполнения, оставьте её в первой колонке и не запускайте таймер.

Когда Codex открыт в папке с подключённым MCP, можно попросить его:

```text
/task Создай задачу в проекте «<название проекта>»:
<кратко опиши задачу>
```

Codex найдёт проект через `list_projects`, создаст задачу и ответит её номером и ссылкой. Если запрос содержал только просьбу зарегистрировать задачу, она останется в первой колонке.

Когда пользователь поручает выполнить работу, после создания или загрузки задачи агент вызывает `take_task_into_work`, затем работает с файлами открытого проекта. Команда `/task <описание>` создаёт новую карточку; `/task <номер>` продолжает указанную. Указывать `project_id` для получения задачи по глобальному номеру не нужно.

Если Codex не находит сервер `armory` в `/mcp`, проверь `codex mcp list`, доверие к проекту и перезапусти сессию. Для локального stdio-подключения проверь `.env` с `MCP_API_KEY`, `ARMORY_BASE_URL` и `MCP_LOCAL_ASSIGNEE_NAME`; для HTTP-подключения проверь API-ключ в `X-MCP-API-Key`. На локальном HTTP-сервере (`AUTH_REQUIRED=false`) без подтверждённого пользователя используется `MCP_LOCAL_ASSIGNEE_NAME`; в публичном режиме выполни авторизацию командой `codex mcp login armory`.

Номер задачи глобальный в пределах ARMory, поэтому `project_id` не нужен при получении или взятии задачи в работу.

## Безопасность и совместимость

- Если на сервере задан `MCP_API_KEY`, HTTP-вызов с OAuth дополнительно должен передать этот ключ через `X-MCP-API-Key`. Старый формат `Authorization: Bearer <mcp-api-key>` продолжает работать отдельно.
- OAuth-пользователь определяется при браузерном входе и сохраняется в MCP OAuth-токене. API-ключ подтверждает доступ, но не личность: в публичном режиме вызов только с ключом не назначает инициатора и не блокирует создание задачи. Локальный HTTP-сервер (`AUTH_REQUIRED=false`) без подтверждённого пользователя и stdio-сервер используют `MCP_LOCAL_ASSIGNEE_NAME`. Подтверждённый HTTP-пользователь имеет приоритет перед локальной настройкой.
- Для внутренних вызовов API ключ принимается только на маршрутах чтения проектов, исполнителей, статусов и задач, создания и обновления задач, добавления вложений, учёта времени агента, а также регистрации настроенного MCP-исполнителя.
- Храни ключи в окружении или менеджере секретов; не коммить конфигурацию MCP с секретами.
- Для Streamable HTTP указывай точный URL с завершающим слэшем: `/mcp/`.

## Правила для AGENTS.md других проектов

Этот блок задаёт порядок работы агента. Само подключение ARMory настраивается отдельно в MCP-конфигурации клиента.

```markdown
## Работа с ARMory Kanban через MCP

- Если в промпте указаны пути к проектам или файлам, сохраняй их без изменений как вводные во вложениях задачи: передавай все пути в `create_task.input_paths`, а для существующей задачи — в `update_task.input_paths`. Не ограничивайся описанием, не подставляй пути из окружения и не читай файлы ради добавления ссылки. При `input_paths_errors` сообщи об ошибках вложений; не создавай повторно уже созданную карточку.

- Используй подключённый MCP-сервер ARMory и его инструменты. Названия вызывай ровно так, как их показывает клиент; например, в Codex это может быть mcp__armory__get_task. При недоступности сервера или ошибке инструмента сообщи точную ошибку; не переключайся на другой инстанс без указания пользователя.
- Создавай новую карточку только если сообщение содержит буквальную команду /task. Если пользователь явно просит работать с существующей задачей, загрузи её по номеру. Если сразу после /task указан номер, в том числе с #, используй эту существующую задачу; если номера нет — создай новую. Без этих условий карточки автоматически не создавай.
- Если пользователь прислал ссылку вида /projects/{project_id}/kanban?task={task_id}, извлеки оба ID и вызови get_task с task_id: он глобальный, project_id в этот вызов не передаётся. Сверь project_id из ссылки с project_id полученной задачи. При несовпадении не изменяй карточку и сообщи об ошибке. После загрузки сообщи номер, проект, название, описание, статус и приоритет. Название проекта бери из project_name; если оно не вернулось, укажи project_id.
- Для новой задачи найди проект через list_projects, если он не указан однозначно. Передавай реалистичную оценку estimated_minutes. MCP назначает AI Assistant и определённого пользователя, если удалось его найти. Если create_task возвращает assignee_prompt_required: true, сообщи, что карточка создана с AI Assistant, и предложи указать исполнителя. После ответа пользователя загрузи текущих исполнителей через get_task и обнови полный список через update_task.assignee_names, сохранив AI Assistant. Исполнителей передавай отображаемыми именами.
- Если пользователь просит только зарегистрировать задачу, оставь её в первой колонке без запуска таймера. Если поручено выполнение, вызови take_task_into_work и начинай работу после успешного ответа: карточка переходит в «В работе», запускается таймер work.
- При любой паузе в работе или тестировании, ожидании ответа пользователя и перед финальным ответом вызови pause_task_time независимо от статуса карточки. При ожидании ответа и временной паузе передавай completed=false; после завершения порученной работы и проверок перед финальным ответом — completed=true. Статус времени не зависит от колонки Kanban. Для продолжения того же этапа используй start_task_time с фазой work или testing. Паузы не входят в фактическое время.
- После реализации переведи карточку в «Тестирование» через update_task и проведи собственные проверки: смена стадии запускает таймер testing. Если карточка уже в «Тестировании», для возобновления проверок вызови start_task_time с фазой testing. Если нужны исправления, вызови take_task_into_work, а перед повторными проверками снова переведи карточку в «Тестирование».
- После собственных проверок вызови pause_task_time с completed=true и запиши результат через update_task. Оставь карточку в «Тестировании» с остановленным таймером. В «Деплой» и финальный статус переводи только по прямой просьбе пользователя. Изменение описания, результата, исполнителей или повторная передача текущего статуса не возобновляют таймер.
- Если пользователь снова просит доработать эту задачу, загрузи её через get_task и вызови take_task_into_work: карточка возвращается в «В работе», начинается новый рабочий интервал, накопленное время сохраняется.
- Для ручной записи времени существующей или выполненной задачи вызывай update_task_time. Передавай только те итоги, которые нужно задать: estimated_minutes, work_minutes, testing_minutes и/или actual_minutes. Все значения — в минутах. Не записывай их в описание или результат задачи.
- В update_task.assignee_names передавай полный желаемый список исполнителей: он заменяет текущий. Не удаляй текущих исполнителей без указания пользователя.
- Не хардкодь адреса и ключи. Для stdio-подключения ARMORY_BASE_URL задаётся в окружении MCP-процесса; для удалённого HTTP-подключения URL сервера задаётся в MCP-конфигурации клиента и должен оканчиваться на /mcp/. Секреты не коммить.
```
